# CMS and persistence options for the static Sâm Ngọc Linh site

**Decision context.** The current public site is a collection of static HTML pages. The ticket adds one private owner-editor, structured product/category/detail/news content, authored page sections, public anonymous reading, and changes visible immediately after publishing. This is a managed-service comparison; the options retain the current visual frontend but need content-driven rendering work.

**Status.** Research only; no CMS has been selected. This file is currently uncommitted. The repository has no commits, so no research branch was pushed rather than including the user's untracked site files in a new history.

## Recommendation

Use **Sanity Content Lake + Sanity Studio** for the first implementation. Model products, categories, product details, news, and pages as typed documents, and pages as an ordered array of allowed section objects. Keep the existing site design as the renderer for those section types. An authenticated owner edits and publishes in Studio; the public site reads only published documents from the anonymous read API/CDN. This gives a managed editor, structured content and immediate API freshness without operating a custom database/server. It does **not** create a freeform drag-and-drop page designer: editors choose and order designed sections; layout geometry/responsiveness remains in the site’s code.

A public Sanity dataset is compatible with public read access; the editor requires a Sanity account/project membership. Do not put a write token in browser code. The Free plan is currently $0 and supports public datasets, but has hard usage caps; exceeding a cap can block affected functionality. Private datasets require Growth (listed at $15/seat/month). Confirm current limits/pricing before production. ## Suggested content model

- `product`: name, slug, category reference(s), summary, detail content, image references, publication status.
- `category`: name, slug, description, image and ordering.
- `news`: title, slug, date, summary, body, image, publication status.
- `page`: slug and an ordered `sections` array whose allowed object types map to existing designed components (for example hero, product grid, rich text, image/text feature, news list). Give each section only its supported content/options.
- Keep responsive behavior and visual constraints in code; avoid storing arbitrary pixel coordinates as the canonical mobile/desktop layout unless an actual freeform design tool is a firm requirement.

Before implementing, confirm whether “immediate” means content appears on the next public page request (Sanity/API renderer) or requires rebuilding static output. This is the key architecture choice: if the site must remain entirely pre-rendered static files, use a deploy webhook/rebuild after publishing (or choose Git-backed content), and accept deploy latency. Also note Sanity Studio validation runs client-side only; if API writes are introduced, validate those separately.
